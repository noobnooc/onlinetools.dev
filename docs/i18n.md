# Translations

The site ships in **18 languages**. English is canonical; every other locale
mirrors its shape, enforced by the type system.

| | | | | | |
| --- | --- | --- | --- | --- | --- |
| `en` English | `zh` 中文 | `ja` 日本語 | `ko` 한국어 | `es` Español | `fr` Français |
| `de` Deutsch | `pt` Português | `ru` Русский | `it` Italiano | `tr` Türkçe | `pl` Polski |
| `vi` Tiếng Việt | `id` Bahasa Indonesia | `nl` Nederlands | `th` ไทย | `uk` Українська | `hi` हिन्दी |

Improving a translation is one of the most useful contributions you can make
here, and one of the easiest: it touches no logic, and every string you fix is
read by someone who currently sees an awkward one.

## How it fits together

There are **three** layers of translatable text, deliberately separate because
they have different costs and different fallback behavior:

| Layer | Where | Fallback if missing |
| --- | --- | --- |
| **UI chrome** — nav, buttons, page headings | `locales/<loc>.ts` → `ui` | English, at runtime |
| **Tool-internal labels** — control names, stat tiles, hints | `locales/<loc>.ts` → `tl` | English, at runtime |
| **Tool names + one-line descriptions** | `locales/<loc>.ts` → `tools` | Registry English |
| **Long-form About/FAQ per tool** | `tools/content.<loc>.ts` | English, and the section is marked `lang="en"` |

Plus `categories` (the ten category labels) in each locale file.

URL shape: English lives at the root (`/t/json-formatter`), every other locale
under its own prefix (`/zh/t/json-formatter`). `/en/*` intentionally 404s — no
duplicate of the root. The prefix is matched by `src/params/lang.ts`, which only
matches known non-English codes, so `/tools` is never read as a language.

`locales/en.ts` is the canonical catalog and *types* the others:

```ts
export interface Messages {
	code: string;                                  // BCP-47 code = URL prefix
	name: string;                                  // endonym, shown in the switcher
	ui: Record<keyof typeof en.ui, string>;
	tl: Record<keyof typeof en.tl, string>;        // flat namespace shared by all tools
	categories: Record<ToolCategory, string>;
	tools: Record<string, ToolL10n>;
}
```

Because `ui` and `tl` are keyed off English, **a missing key is a compile
error** — `pnpm check` catches it before review does. English tool names and
descriptions are derived from the registry rather than duplicated.

Interpolation is `{name}` placeholders, substituted by `t()` / `tt()`:

```ts
themeTitle: 'Theme: {mode} — click to switch',
wcCharsHint: '{n} without spaces',
```

Keep every placeholder — dropping one leaves a literal `{n}` on the page.

## Improving an existing translation

1. Open `src/lib/i18n/locales/<code>.ts`.
2. Find the string. Keys are grouped by area with comments (`// Chrome`,
   `// About / Why page`, `// Word counter`, …) and mirror the order in
   `en.ts`, so the English original is easy to compare side by side.
3. Fix it. Keep the key, keep every `{placeholder}`.
4. `pnpm check && pnpm test`, then open a PR describing what was wrong — "the
   Turkish for *escape* was the travel sense, not the string sense" tells a
   reviewer who doesn't speak Turkish everything they need.

Small, focused PRs are perfect here. You don't have to fix a whole locale.

## Translating a tool's long-form content

Each tool page carries hand-written About paragraphs and FAQs. English lives in
`src/lib/tools/content.ts`; translations live in `content.<locale>.ts`, keyed by
the same tool slug, and are loaded dynamically per locale by
`routes/[[lang=lang]]/t/[slug]/+page.ts`.

These files are **partial by design** — a tool with no entry in your locale
falls back to the English copy, and the page marks that section `lang="en"` so
screen readers and search engines aren't told a lie. So translating five tools
is a perfectly good PR; you don't have to do all 44.

```ts
// src/lib/tools/content.zh.ts
const content: Record<string, ToolContent> = {
	'json-formatter': {
		about: [ '…', '…' ],
		faqs: [ { q: '…', a: '…' } ]
	}
};
export default content;
```

Translate the *meaning*, not the words. These paragraphs exist to answer a real
question for someone who arrived from a search result in their own language —
if a more natural phrasing serves that better than a literal rendering, use it.
Keep technical terms (JSON, Base64, RFC 4648, JWT) in their conventional form
for your language, which is often the English one.

## Adding a new locale

Bigger job, but mechanical. Say you're adding Swedish (`sv`):

1. **`src/lib/i18n/codes.ts`** — add `'sv'` to `EXTRA_LOCALES`, plus entries in
   `OG_LOCALES` (`sv_SE`, territory-qualified — Open Graph requires it) and
   `LOCALE_NAMES` (`'Svenska'`, the endonym). Miss the last one and the
   language switchers render `undefined`.
2. **`src/lib/i18n/locales/sv.ts`** — copy `en.ts`, translate `ui` and `tl`,
   translate `categories`, and write the `tools` block by hand (English derives
   its names from the registry; yours can't). The `Messages` type will tell you
   about every key you missed.
3. **`svelte.config.js`** — the `prerender.entries` list seeds locale roots for
   the crawler. Tool pages declare their own entries, so this is a
   belt-and-braces list; add `/sv` if you want the crawler seeded from it.
4. `pnpm build` — this prerenders 44 tools × every locale. It's the real test.
5. Visit `/sv`, `/sv/tools`, `/sv/about` and a few tool pages. Check the
   sidebar, the `⌘K` palette (it matches localized names too), and that nothing
   overflows — German and Vietnamese labels run long, and CJK runs short.

Optionally then `src/lib/tools/content.sv.ts` and its loader entry in
`routes/[[lang=lang]]/t/[slug]/+page.ts` for long-form copy.

Everything else — hreflang alternates, OG locale tags, the sitemap, canonical
URLs — is generated from `LOCALES` and needs no further edits.

**Please only add a language you actually speak.** Machine-translated locales
are worse than no locale: they look supported, rank in search, and then read
like spam to the people who land on them.

## Style guide

- **Match the English voice**: plain, direct, technically precise. Not
  marketing, not academic. No exclamation marks, no superlatives.
- **Keep technical terms conventional.** Developers search in a mix of their
  language and English; translating "Base64" or "regex" into something nobody
  types makes the page unfindable.
- **Mind the length.** Sidebar labels, segmented controls and badges have
  limited room. If the natural translation is much longer than the English,
  find a shorter natural phrasing rather than letting it wrap.
- **Use your language's real typography** — CJK full-width punctuation, French
  spacing before `!?:;`, Spanish `¿¡`, proper quotation marks.
- **Formality**: match how technical documentation is normally written in your
  language (informal `du`/`tú`/`ты` where that's the norm for dev tools).
- The `.` in `onlinetools.dev`, the brand name, and keyboard shortcut symbols
  (`⌘K`) are never translated.

## Checklist

```
[ ] Every {placeholder} preserved
[ ] No key added or removed relative to en.ts (types will tell you)
[ ] pnpm check → 0 errors
[ ] pnpm test  → passes
[ ] pnpm build → prerenders
[ ] Spot-checked in the browser: sidebar, palette, a tool page, About
[ ] Nothing overflows or wraps badly in either theme
```
